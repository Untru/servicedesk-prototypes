Список заявок на больших объёмах: план

Как сделать «Все заявки», фильтры по спискам значений, сортировки и пагинацию так, чтобы на десятках и сотнях тысяч заявок рабочее место не деградировало, а поиск и фильтры действовали по всем страницам.

Что есть сейчас

  • Очередь HTML-рабочего места показывает только свои заявки, по 20 строк. Страница строится запросом ПЕРВЫЕ (смещение + 21), и лишнее отрезается в памяти: чтобы показать 50-ю страницу, база читает тысячу строк. На глубоких страницах это линейно дорожает.
  • Поиск — ПОДОБНО "%текст%" по номеру и теме: такой шаблон не использует индекс и читает всю таблицу заявок.
  • Из нужных полей индексирован только Клиент. У Статус, ТекущийИсполнитель, ДатаОкончанияПлан индекса нет.
  • Порядок — по состоянию SLA и сроку; для этого к каждой строке присоединяется регистр сд_СостояниеSLAЗаявок.
  • Доступ ограничен RLS БСП (клиент, проект, автор). Для режима «Все» в расширении уже есть роль сд_ПросмотрВсехЗаявок.

Принципы

  1. Сначала фильтр, потом страница. Все условия (режим, статусы, клиенты, исполнители, поиск) уходят в запрос параметрами, база возвращает только нужную страницу. В HTML никогда не приходит весь список.
  2. Пагинация по ключу, а не по смещению. Следующая страница начинается «после последней показанной строки» по ключу сортировки, а не «пропусти N строк». Стоимость любой страницы одинакова.
  3. Два шага на страницу. Первый лёгкий запрос выбирает 25–50 ссылок по фильтру и сортировке. Второй дочитывает для них клиента, исполнителя, SLA и прочее. Тяжёлые соединения делаются только для строк страницы.
  4. Счётчики отдельно и с кэшем. «из 1 340» и счётчики фасетов считаются отдельным запросом и кэшируются на 30–60 секунд для того же набора фильтров. Если подсчёт дорогой, показываем «1 000+».
  5. Права не обходим. Запросы остаются РАЗРЕШЕННЫЕ, без привилегированного режима; «Все заявки» доступны только при роли сд_ПросмотрВсехЗаявок. Остальное ограничит RLS.

Фильтры по спискам значений

Каждый фильтр — массив значений, пустой массив означает «без ограничения». Чтобы не строить текст запроса динамически, условие пишется с флагом:

ГДЕ (&ВсеСтатусы ИЛИ Задачи.Статус В (&Статусы))
  И (&ВсеКлиенты ИЛИ Задачи.Клиент В (&Клиенты))
  И (&ВсеИсполнители ИЛИ Задачи.ТекущийИсполнитель В (&Исполнители))
  И (&ВсеЗаявки ИЛИ Задачи.ТекущийИсполнитель = &Я)
  И НЕ Задачи.ПометкаУдаления

Фильтр по исполнителям показывается только в режиме «Все». Выбор пользователя (режим, фильтры, сортировка) сохраняется в его настройках формы.

Поиск по всем страницам

  1. Номер. Если введено число или «№…», ищем по номеру точно или по префиксу (Номер ПОДОБНО "217%") — это работает по индексу и мгновенно.
  2. Текст. Тема, клиент и описание ищутся через полнотекстовый поиск платформы (у реквизитов он уже включён). Индекс обновляет регламентное задание БСП, результат — список ссылок, к которому применяются фильтры и сортировка.
  3. Запасной путь. Если полнотекстовый индекс выключен, используем ПОДОБНО, но только вместе с другими фильтрами. Строка поиска срабатывает от 3 символов с задержкой 300 мс.

Счётчики и фасеты

  • Счётчики по статусам — один запрос СГРУППИРОВАТЬ ПО Статус с теми же фильтрами, кроме фильтра по статусу. По клиентам и исполнителям — первые 20 значений по количеству и поиск внутри списка.
  • Все счётчики кэшируются на 30–60 секунд по ключу «пользователь + фильтры» и сбрасываются при записи заявки этим пользователем.

Индексы — решение владельца

Нужна реструктуризация базы. Индексы по Статус, ТекущийИсполнитель и ДатаОкончанияПлан («Индексировать с доп. упорядочиванием») меняют структуру таблицы заявок. Текущий путь поставки через ibcmd-rs реструктуризацию отклоняет, поэтому этот шаг нужно согласовать отдельно: штатный ibcmd или Конфигуратор в окно обслуживания. Без индексов этапы 1–2 всё равно дают выигрыш, но сортировка по сроку и статусу на сотнях тысяч заявок будет медленнее.

Этапы

1
1–2 дня
Режим «Мои / Все» (по роли), фильтры по спискам статусов, клиентов и исполнителей, четыре сортировки, ключевая пагинация и двухшаговый запрос в HTML-рабочем месте. Поиск по номеру — по индексу, по тексту — пока ПОДОБНО вместе с фильтрами. Настройки запоминаются.
2
0,5–1 день
Счётчики и фасеты с кэшем, «из N» или «1 000+».
3
1 день + окно
Индексы по статусу, исполнителю и сроку — после решения владельца о реструктуризации.
4
1 день
Полнотекстовый поиск по теме, клиенту и описанию через индекс платформы и регламентное обновление.
5
0,5 дня
Замер на копии базы со 100 и 500 тысячами заявок (генератор данных, технологический журнал): цель — страница ≤ 0,3 с, первое открытие ≤ 1 с, поиск по номеру ≤ 0,2 с. Нужно разрешение владельца на этот замер, сейчас тесты не запускаются.
Что выбрать сначала. Интерфейс фильтров — любой из прототипов Ф1–Ф3: серверная часть для них одна и та же (этап 1). Предлагаю начать с этапа 1 на выбранном прототипе, а индексы и полнотекстовый поиск решить после замера.
